Get cantobuddy.com into Google Search Console

Verify the domain, then submit the sitemap. About two minutes, done once.

Both verification methods are already live. There is nothing to upload. The homepage carries the meta tag with the token qrG0jeGcYgQqTjw6GqxSkJZ_u7RdvliFJmacydYG90Y, and both google2d4390410b35314f.html and google5851b3aeb7bd5d4e.html are real files on the site, byte-identical to the ones Google hands you. Whichever method Search Console showed you, go straight to clicking Verify.

The steps

  1. Open Search Console Go to search.google.com/search-console and sign in with the Google account that should own this site. This is the only part nobody else can do for you.
  2. Add a property Click Add property. Pick the right-hand box — URL prefix, not the Domain box on the left — and enter exactly:
    https://cantobuddy.com/
  3. Whichever method it offers, it is already done Both routes are live, so there is nothing to fill in on this screen:
    Meta tag — the tag is in the homepage right now. If Search Console shows you a tag to paste, don't paste it anywhere. It is already there.
    HTML file — the file is deployed and serving. Ignore the download.
  4. Click Verify Google checks by fetching https://cantobuddy.com/ for the meta tag, or https://cantobuddy.com/google2d4390410b35314f.html for the file. Both answer correctly, so there is nothing to upload and no redeploy.
  5. Submit the sitemap Once verified, open Sitemaps in the left menu, type sitemap.xml into the box, and click Submit. It should read "Success — 1,300+ discovered URLs" within a few minutes.

Why 1,300+

Four language trees — English 180, Filipino 180, Chinese 180, Indonesian 180 — plus the four guides in every language, plus word pages and category pages. The number comes straight from the live sitemap, so if it differs slightly, the sitemap changed rather than the submission failing.

If something goes wrong

"…indicates that your site might have been hacked"

This is the message you saw first, and it was a real bug in the site — not a wrong token. The server used to answer the verification content for any filename, and a site that does that is indistinguishable from one rigged to claim properties, so Google refused it on principle.

It is fixed: the file is now a single real file, and every other google*.html correctly returns 404. Press Verify again. If Google holds the suspicion for a while, use the DNS fallback below instead.

Check by hand, any time

Both routes are visible in an ordinary browser. The homepage should contain this line — view source, or search the page for google-site-verification:

<meta name="google-site-verification" content="qrG0jeGcYgQqTjw6GqxSkJZ_u7RdvliFJmacydYG90Y" />

And https://cantobuddy.com/google2d4390410b35314f.html should show exactly one line:

google-site-verification: google2d4390410b35314f.html

A 404, or a missing tag, means the deploy has not landed yet — wait a minute and reload.

Fallback: the DNS record (most robust)

In Search Console, choose the Domain property instead and verify with a TXT record added in Cloudflare. It needs no file and no deploy, it covers the whole domain including subdomains, and it does not depend on the app being up at the moment Google looks — which is the one thing that has already gone wrong once here.

The meta tag works only because it is written into the homepage by hand

The site generator can emit a verification tag from an environment variable, but only on the pages it renders itself — and the homepage is a static file that shadows them, so that route can never verify https://cantobuddy.com/. The tag was therefore added directly to that file. If the homepage is ever rebuilt from a template, check the tag survived; seo-pillar-test asserts it is there, so a regression fails loudly rather than verification lapsing quietly.

What this does and doesn't do

Submitting does not push your pages into Google, and it does not improve ranking. Google already knows the sitemap exists — robots.txt points at it, which is Google's own documented discovery path. What Search Console gives you is visibility: which pages Google has indexed, which it has not, and any crawl errors.

Bing and Yandex were already notified directly through IndexNow, so they did not need any of this.
